# Output-Only Fields

Resource fields are owned by either the client or the server. This document describes how to define and annotate server-owned (output-only) fields.

## Guidance

Fields **must** have a single owner: either the client or the server. Server-owned fields **must** be marked as output-only using `readOnly: true` in OpenAPI.

Output-only fields are appropriate when the server:
- Generates unique identifiers (UUIDs, auto-increment IDs)
- Calculates derived values (totals, aggregations)
- Assigns system values (IP addresses, ports)
- Tracks resource metadata (creation time, update time)

### OpenAPI annotation

Output-only fields **must** use `readOnly: true`:

```yaml
Product:
  type: object
  properties:
    name:
      type: string
      description: "Resource name"
    title:
      type: string
      description: "Product title (client-settable)"
    uid:
      type: string
      description: "System-generated unique identifier"
      readOnly: true
    create_time:
      type: string
      format: date-time
      description: "Resource creation timestamp"
      readOnly: true
    update_time:
      type: string
      format: date-time
      description: "Last update timestamp"
      readOnly: true
```

### Effective values

When a server computes an effective value for a field that the client can also set, use the `effective_` prefix for the output-only field:

```yaml
VirtualMachine:
  type: object
  properties:
    ip_address:
      type: string
      description: "Requested IP address (optional, client-settable)"
    effective_ip_address:
      type: string
      description: "Actual assigned IP address"
      readOnly: true
```

This pattern allows clients to request a value while the server returns what was actually assigned.

## Rationale

Clear field ownership prevents conflicts between client-specified and server-generated values. The `readOnly` annotation enables:
- **API documentation**: Clearly shows which fields clients cannot set
- **Client generation**: Code generators can mark fields appropriately
- **Validation**: Servers can reject requests attempting to set read-only fields
- **Declarative clients**: Supports tools that compare desired vs actual state

The `effective_` prefix pattern makes it clear when a server overrides or computes a value differently from what a client requested.
