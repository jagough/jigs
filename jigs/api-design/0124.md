# Resource Hierarchy

Resources in an API are often related to other resources through parent-child relationships. This document describes how to model resource hierarchies and associations.

## Guidance

A resource **must** have at most one canonical parent. The canonical parent is reflected in the resource's name pattern and determines the resource's place in the API's hierarchy.

If a resource has many-to-one relationships with multiple resource types, it **must** choose at most one of them to be the canonical parent. The resource **may** be associated with other resources through additional fields.

Examples:
- `vendors/{vendor}/products/{product}` - Product's canonical parent is Vendor
- `locations/{location}` - Location has no parent (top-level resource)

### Additional associations

Resources **may** have many-to-one relationships with multiple resource types. Additional associations beyond the canonical parent **should** be represented as resource reference fields (see JIG-123).

Example:
```yaml
Product:
  type: object
  properties:
    name:
      type: string
      description: "Canonical resource name"
      example: "vendors/acme-corp/products/widget-42"
    parent:
      type: string
      description: "Canonical parent (vendor)"
      x-resource-reference: "marketplace.jagough.com/Vendor"
    manufacturer:
      type: string
      description: "Additional association (not the parent)"
      x-resource-reference: "marketplace.jagough.com/Manufacturer"
```

### Many-to-many relationships

For many-to-many relationships, use one of these approaches:

**Repeated resource references** (preferred):
```yaml
Book:
  properties:
    name:
      type: string
      example: "publishers/penguin/books/moby-dick"
    parent:
      type: string
      x-resource-reference: "library.googleapis.com/Publisher"
    authors:
      type: array
      items:
        type: string
        x-resource-reference: "library.googleapis.com/Author"
```

**Association resource** (alternative):
Create a separate resource representing the association:
- `publishers/{publisher}/books/{book}`
- `authors/{author}/books/{book}`

Choose the approach that best reflects the primary access pattern.
