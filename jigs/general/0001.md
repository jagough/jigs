# JIG Purpose and Guidelines

JIGs (Jonathan's Implementation Guidance) provide a corpus of concise, structured documentation for service design and development. This document defines what JIGs are, their purpose, and how they are managed.

JIG's came about after trialling the use of google AIP's in devlopment of HTTP API services and clients, however I soon found issues with this approach because the google AIP's are designed with gRPC services in mind.
Therefore I wanted to create my own pattern library, where each pattern was described in such a way that was easy for myself and agents to consume. 

## Guidance

### What is a JIG?

JIG stands for **Jonathan's Implementation Guidance**, which is a design document providing high-level, concise documentation for service development and API design patterns.

JIGs serve as the **source of truth** for implementation decisions, patterns, and standards. They enable both human developers and AI agents to reference authoritative guidance when implementing features or designing services.

### Types of JIGs

JIGs **must** fall into one of the following categories:

- **Guidance JIGs**: Provide instruction for API design, service architecture, or implementation patterns. These came be used by as a basis for review comments.
- **Meta JIGs**: Describe the JIG process itself or organizational standards

Additional categories **may** be added as the scope expands.

### States of JIGs

JIGs **must** have one of the following states in their front matter:

- **draft**: The JIG is under active development and not yet finalized
- **approved**: The JIG has been reviewed and is the current standard
- **deprecated**: The JIG has been superseded by newer guidance but remains for historical reference

JIGs in the `approved` state **must** be followed unless there is explicit, documented justification for deviation.

JIGs in the `deprecated` state **should not** be used for new implementations but **may** be referenced for understanding legacy systems.

### Scope

JIGs initially focus on:

- API design patterns
- Service architecture standards
- Implementation guidance for common scenarios

The scope **may** expand over time to include additional development domains such as:

- Data modeling patterns
- Security best practices
- Testing strategies
- Deployment and operations

### Target audience

JIGs are designed for **two primary audiences**:

1. **Human developers**: Who need clear, concise guidance when designing or implementing services
2. **AI agents**: Who need structured, machine-parsable references to apply patterns and standards autonomously

This dual-audience approach requires JIGs to be both human-readable and consistently structured for programmatic consumption.

## Rationale

### Why JIGs exist

Without a centralized source of truth, implementation standards can drift, become inconsistent, or exist only as tribal knowledge. JIGs address this by:

- **Documenting decisions**: Making implicit standards explicit
- **Enabling consistency**: Providing a reference that ensures similar problems are solved similarly
- **Supporting automation**: Allowing AI agents to apply standards automatically
- **Tracking evolution**: Using versioning and changelogs to show how standards evolve over time

### Why the format matters

The structured format (YAML front matter, required sections, RFC 2119 keywords) enables:

- **Programmatic parsing**: MCP servers can extract and serve JIG content to agents
- **Clear requirements**: RFC 2119 keywords make it unambiguous what is required vs. optional
- **Searchability**: Consistent structure enables efficient searching by topic, category, or requirement type
