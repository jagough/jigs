# JIG Style and Guidance

This document defines the structure, formatting, and authoring guidelines for JIG (Jonathan's Implementation Guidance) documents. JIGs serve as the source of truth for service design and development patterns, providing clear, concise guidance that both humans and AI agents can reference when implementing features.

## Guidance

JIGs **must** follow a consistent structure and style to ensure clarity and usability.

### File structure

JIGs **must** be stored as Markdown files in the `/jigs/` directory. Files **must** be named using a four-digit zero-padded number with the `.md` extension (e.g., `0001.md`, `0042.md`).

JIGs **should** be organized into category subdirectories:

- `/jigs/general/` - Cross-cutting or meta-JIGs
- `/jigs/api-design/` - API design patterns
- `/jigs/service-architecture/` - Service architecture patterns

Additional category directories **may** be created as the scope expands.

### Document structure

JIGs **must** begin with YAML front matter containing:

- `id`: The JIG number (integer)
- `state`: Current status (`draft`, `approved`, or `deprecated`)
- `created`: ISO-8601 date (YYYY-MM-DD)
- `category`: The JIG category
- `permalink`: Short URL path (e.g., `/1`)

The front matter **should** include:

- `updated`: ISO-8601 date of last update
- `tags`: Array of relevant tags
- `redirect_from`: Array of alternative URL paths

JIGs **must** include a top-level heading with the JIG title, followed by an introductory paragraph.

JIGs **must** include a `## Guidance` section containing the primary implementation guidance.

JIGs **should** include the following sections in order:

- `## Examples` - Concrete code examples
- `## Anti-patterns` - Common mistakes to avoid
- `## Rationale` - Reasoning behind the guidance
- `## Related JIGs` - Cross-references to other JIGs
- `## Further reading` - External references
- `## Changelog` - Version history

JIGs **must** use only second-level (`##`) and third-level (`###`) headings within the document body. The title is the only first-level heading.

### Requirement keywords

JIGs **must** use RFC 2119 keywords to indicate requirement levels:

- **must** / **required** - Absolute requirement
- **must not** - Absolute prohibition
- **should** / **recommended** - Strong recommendation
- **should not** - Generally avoided
- **may** / **optional** - Truly optional

These keywords **must** be formatted in **bold** and lowercase.

### Code examples

Code examples **should** be included in the `## Examples` section to demonstrate the guidance concretely.

Examples **should** use syntax highlighting with appropriate language tags in code fences.

Examples **must** be clear, minimal, and focused on illustrating the specific guidance point.

Examples **may** include multiple languages or frameworks when relevant.

### Changelog format

The `## Changelog` section **must** list changes in reverse chronological order (newest first).

Each changelog entry **must** include the date in **bold** (ISO-8601 format) followed by a concise description.

```markdown
## Changelog

- **2025-10-08**: Added versioning guidance
- **2025-10-05**: Initial publication
```

### Referencing JIGs

References to other JIGs **should** use the format `JIG-XXXX` in prose and link to the permalink (e.g., `[JIG-0001](/1)`).

## Examples

### Complete JIG front matter

```yaml
---
id: 42
state: approved
created: 2025-10-08
updated: 2025-10-15
category: api-design
tags:
  - rest
  - http
  - versioning
permalink: /42
redirect_from:
  - /042
  - /0042
---
```

### Using RFC 2119 keywords

```markdown
API endpoints **must** use kebab-case for path segments.

API endpoints **should** include version information in the URL path.

API endpoints **may** support multiple content types via Accept headers.
```

## Rationale

### Consistency enables automation

By following a rigid structure, JIGs can be parsed programmatically by the MCP server, enabling AI agents to search, retrieve, and apply guidance automatically. This makes JIGs not just human documentation but machine-actionable references.

### Anti-patterns prevent common mistakes

Documenting what NOT to do is as valuable as documenting what to do. Anti-patterns help both humans and agents avoid well-known pitfalls.
